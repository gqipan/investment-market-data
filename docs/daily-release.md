# 每日累计数据发布

`daily index release` 每天北京时间 21:40、23:40 和次日 09:00 检查一次。09:00 只检查截至昨天的已闭市交易日，避免盘中把当天误当成已完成会话。每次运行都会读取深交所独立交易日历，找出上一版 Release 之后尚未发布的全部已闭市交易日；没有待发布会话时正常结束，不创建空版本。日历源不可用时工作流失败，而不是把未知状态当成休市。

这个安排用来处理上游延迟：如果周五数据在周五 21:40 或 23:40 尚未齐备，工作失败且不发布；周六 09:00 会继续尝试。周六补齐时仍发布 `data-<周五日期>-r1`，不会给周六生成一个空 Release。若一次积压多个交易日，工作流把连续缺失区间合并为一个补缺批次，Release 以其中最新交易日命名。

## 第一次全量基线

手动触发工作流并设置 `bootstrap=true`。基线使用 `2005-01-01` 作为请求起点，可以包含在指数正式发布前没有观测的明确前缀。生成目录按以下结构保存：

```text
baseline/
cumulative-manifest.json
```

基线中的每份内容寻址数据集必须先通过 manifest SHA-256、`dataset_id`、正文哈希、交易日历和数据类型复验。仓位、账户、现金流、私人报告及服务器配置不属于输入范围。

## 后续每日增量

普通定时运行或手动设置 `bootstrap=false` 时，工作流请求上一版之后的连续缺失交易日，并执行以下步骤：

1. 找到最近一个正式 `data-*` Release，并核对 tag 日期与累计清单中的 `as_of`。
2. 查询交易日历中从上一版次日至当前允许上界之间的全部已闭市交易日；没有缺失会话时直接结束。
3. 下载上一版累计压缩包和 `SHA256SUMS`，复验压缩包哈希及 `cumulative-manifest.json` 中的全部文件清单。
4. 采集连续缺失区间，逐个复验批次内价格、收盘价和估值清单，并且至少 9 条行情必须到达区间末日才继续。
5. 将补缺结果作为不可变批次追加到 `deltas/<末日日期>/`，不覆盖基线或旧批次。
6. 重新生成累计清单、完整累计包、补缺增量包和 `SHA256SUMS`。
7. 先上传为草稿，全部附件成功后再正式发布；任一步失败均不修改上一版，下一次定时检查会重试同一缺失区间。

`cumulative-manifest.json` 保存上一版 tag、上一版累计包 SHA-256、批次顺序以及当前所有文件的 SHA-256。相同日期不能追加两次；修订必须使用新的 release 版本，不能原地覆盖。

## Release 文件

- `index-data-cumulative-<日期>.tar.gz`：完整历史基线和截至当日的全部增量。
- `index-data-delta-<日期>.tar.gz`：本次连续缺失区间的采集结果，便于核对新增变化。
- `SHA256SUMS`：上面两个压缩包的 SHA-256。
- `coverage-report.json` / `.md`：当天来源覆盖、缺口和不支持映射。

下载方应锁定 tag 与 `SHA256SUMS`，不使用漂移的 Latest。Git clone 不包含 Release 附件；需要长期保存时另行归档累计包。
